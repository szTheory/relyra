<objective>
Implement AUTHN-03 metadata-toggle gating in `Relyra.Protocol.Metadata.build_sp_metadata/2`:
gate the existing `<md:KeyDescriptor use="signing">` emission (currently unconditional per
Phase 34 D-05 at `lib/relyra/protocol/metadata.ex:34-36`) AND add an
`AuthnRequestsSigned="true"` attribute on the `<md:SPSSODescriptor>` element (currently at
`metadata.ex:33`) — BOTH conditioned on `Map.get(connection, :sign_authn_requests, false) == true`.

When `sign_authn_requests` is false (or absent), OMIT both the signing `<KeyDescriptor>` and
the `AuthnRequestsSigned` attribute ENTIRELY — do NOT emit `AuthnRequestsSigned="false"`; its
absence is the spec default per OASIS Metadata §2.4.2.

PRESERVE the Phase 34 encryption `<md:KeyDescriptor use="encryption">` emission as
UNCONDITIONAL (D-13). Phase 35 owns ONLY the signing-side gating; Phase 34 still owns the
encryption-side existence.

Purpose: Eliminate the SP-advertises-vs-emits-mismatch threat (T-35-04). Without this gating,
an adopter who toggles `sign_authn_requests: false` would still publish metadata advertising
that requests are signed — silently broadcasting a capability the SP does not exercise. Strict
IdPs (modern ADFS, Microsoft Entra) consume the `AuthnRequestsSigned` attribute to set their
`WantAuthnRequestsSigned` policy; emitting it when the SP is not actually signing causes the
IdP to reject every legitimate unsigned AuthnRequest from this SP. The fix-forward: metadata
truthfully reflects runtime behavior.

Output: Updated `Metadata.build_sp_metadata/2` with conditional emission. Extended
`metadata_test.exs` with toggle-on / toggle-off / encryption-invariant assertions. All existing
metadata test cases preserved and continue to pass (with helper updates where they affirmatively
assert `use="signing"` — see Task 2 for the helper-update mechanics).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| SP metadata XML → IdP metadata consumer | The SP-published metadata document crosses an integration boundary from Relyra into the IdP's metadata-import path. The IdP relies on the `AuthnRequestsSigned` attribute and the presence/absence of the signing `<KeyDescriptor>` to configure its `WantAuthnRequestsSigned` enforcement policy and its inbound-request signature-verification key set. A skew between what metadata advertises and what the SP actually emits at runtime causes the IdP to either reject legitimate unsigned requests (when metadata says signing is on but the SP toggle is off) or accept unsigned requests it should have rejected (when metadata says signing is off but the SP toggle is on). |
| `connection.sign_authn_requests` field → `build_sp_metadata/2` reader | The connection map's `sign_authn_requests` boolean (Phase 32 schema-backed) is the single source of truth for runtime signing behavior. Phase 35 makes metadata read this same field, eliminating the prior split where Phase 34 unconditionally advertised signing capability while Phase 32 conditionally exercised it. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-35-04 | Spoofing | `Relyra.Protocol.Metadata.build_sp_metadata/2` (signing-side advertisement) | mitigate | Gate BOTH the `<md:KeyDescriptor use="signing">` emission AND the `AuthnRequestsSigned="true"` attribute on the same boolean (`Map.get(connection, :sign_authn_requests, false) == true`) — single boolean drives both metadata signals AND the runtime signing path (via Plan 35-05 / `start_login/3`). The two metadata signals can never disagree with each other (same source) and can never disagree with runtime behavior (same source as the binding-layer signer decision in Plans 35-02 / 35-05). Verified by Task 2's new test cases: (a) toggle-on emits both signals; (b) toggle-off omits both signals; (c) absent-key (default-false via `Map.get`) treated identically to explicit-false; (d) AuthnRequestsSigned attribute is on the SPSSODescriptor element, not stray on a child. The "advertise capability ≠ exercise capability" skew is structurally eliminated, not merely tested-around. |
| T-35-04b | Tampering | `AuthnRequestsSigned` attribute value | accept | Phase 35 emits the literal string `AuthnRequestsSigned="true"` — there is no path that emits `AuthnRequestsSigned="false"` (D-12: absence is the spec default, presence-equal-to-true is the only published form). An attacker tampering with the SP's served metadata XML to flip the attribute value would require write access to the host's metadata-publication path, which is out-of-scope for Phase 35 (Phase 35 is the producer; metadata serving is an adopter concern). The metadata XML is not signed by Relyra (SAML metadata signing — `<ds:Signature>` over `<md:EntityDescriptor>` — is a v1.4 candidate, not in v1.3 scope). Adopters who require metadata-signing can sign their published metadata via existing XML-DSig tooling at deploy time; Phase 35 produces the SignedInfo-friendly bytes (no whitespace surprises in the descriptor blocks). |
| T-35-04c | Information Disclosure | metadata XML body | accept | The signing `<md:KeyDescriptor>` carries the SP's PUBLIC signing certificate (base64-of-DER of `:sp_signing_cert_pem`) — by spec definition, this is meant to be published. No private key material is sourced or referenced by `build_sp_metadata/2` (the function reads `:sp_signing_cert_pem` and `:sp_encryption_cert_pem`, never the `_pem` private-key variants). The Phase 34 invariant ("PUBLIC certs only — read :sp_signing_cert_pem / :sp_encryption_cert_pem ... must not source any private key material" — `metadata.ex:21-23`) is preserved unchanged. |
| T-35-04d | Repudiation | toggle-state changes on a Connection | accept | Phase 32 already audits `sign_authn_requests` toggle changes via the Connection update audit-row co-commit (CLAUDE.md "Audit co-commit" invariant; Phase 32 D-10/D-11). Phase 35 only READS the field at metadata-build time; it does not mutate the toggle and does not introduce a new audit surface. The audit trail for "when did this SP start advertising signed AuthnRequests" is the existing Connection update audit row chain — no new audit shape is needed because no new mutation is introduced. |
| T-35-04e | Denial of Service | absent / malformed connection map | mitigate | `Map.get(connection, :sign_authn_requests, false)` is total-function safe: it returns `false` for any input that is not the literal boolean `true` (after the explicit `== true` comparison). Nil, missing key, string "true", atom :true_string — all collapse to `false` (omit-signing path). The function cannot raise based on the toggle value. The encryption cert / signing cert path is already nil-safe via Phase 34's `cert_body/1` helper (returns "" on absent / bad PEM; never raises). Combined: there is no input to `build_sp_metadata/2` that causes a crash on the signing-gating decision path. The function returns a binary in all cases. |
