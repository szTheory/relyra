<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Relyra verified principal -> LedgerLoop mapper | Relyra hands verified identity data to host-owned mapping code. |
| Mapper result -> session adapter | Host user data crosses into session/receipt establishment. |
| Receipt rows -> evaluator/support evidence | Receipt content may be displayed by later phases and must be safe now. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-52-01 | Spoofing | `LedgerLoop.Relyra.UserMapper` | mitigate | Mapper only runs from Relyra behaviour seam with verified principal data and rejects unknown principals without creating users. |
| T-52-02 | Elevation of privilege | group/role interpretation | mitigate | Group and role data comes from seeded LedgerLoop memberships, not assertion-controlled authorization decisions. |
| T-52-03 | Information disclosure | `LoginReceipt` payload | mitigate | Tests assert no raw XML, PEM, SAMLResponse, RelayState, FakeIdP, Keycloak, or private key text in receipts. |
| T-52-04 | Tampering | parser bypass | mitigate | Mapper/session code must not parse XML; Relyra remains the only SAML parse/verification path. |
| T-52-05 | Spoofing | trust-source confusion | mitigate | No document `KeyInfo` usage; trust verification happens before mapper/session callbacks. |
| T-52-06 | Tampering / Elevation of privilege | request-derived table selection | transfer | Plan 52-04 owns fixed request/replay wrappers. |
| T-52-07 | Spoofing | replay acceptance | transfer | Plan 52-06 proves replay insertion through configured Ecto replay store. |
| T-52-SC | Tampering | package installs | accept | No package-manager installs are planned. |
</threat_model>
