<objective>
Complete Phase 3 integration by making request-intent and replay controls first-class in the public orchestration flow (`start_login/3`, `consume_response/3`) while keeping protocol-core validation order strict and framework-agnostic.
</objective>

<threat_model>
  <threat id="TM-03-03-INRESPONSETO-BYPASS" severity="high">
    If request intent is optional or fetched inconsistently, mismatched `InResponseTo` values can pass validation in SP-initiated flows.
  </threat>
  <threat id="TM-03-03-REPLAY-CONSUME-GAP" severity="high">
    If replay consume and request-intent consume are not enforced atomically in the success path, duplicate assertions may establish sessions multiple times.
  </threat>
  <threat id="TM-03-03-CORE-COUPLING-REGRESSION" severity="medium">
    Pulling resolver/storage framework details into protocol core can break decoupling guarantees and increase attack surface.
  </threat>
  <mitigations>
    - Wire `start_login/3` to persist intent through `RequestStore.put_intent/3` with relay/request identifiers and expiry metadata.
    - In `consume_response/3`, resolve intent from explicit map (compatibility) or store fetch by relay-state, then enforce replay consume and request consume before returning `{:ok, login_result}`; if either consume operation fails, return typed error and never return `{:ok, _}`.
    - Keep correlation checks in `ValidationPipeline.validate_request_correlation/3` unchanged for `:relay_state_missing`, `:relay_state_mismatch`, and `:in_response_to_mismatch`.
    - Keep resolver integration map-based (`ConnectionResolver.resolve_connection/2`) and avoid any Phoenix/Ecto-specific types in `lib/relyra/protocol/*`.
    - High-severity threats are blocking under ASVS L1 policy; do not mark this plan complete unless all verification commands pass.
  </mitigations>
  <verification_commands>
