# Phase 57.1: Code Review Report

**Reviewed:** 2026-06-14T06:16:35Z
**Depth:** standard
**Files Reviewed:** 9
**Status:** issues_found

## Summary

Reviewed the FakeIdP demo harness hardening work: keypair loader, SAML Response
signer, web controller (login/SSO), the login template, and the new
`Relyra.TestSupport.Poll` helper plus tests.

The harness is correctly scoped as a non-trust-boundary test artifact, and the
core invariants hold up under tracing:

- **Digest stability of escaping is sound.** `response_xml/3` is the single
  interpolation site, called three times with identical escaping, so escaped
  values flow into the digested `<Assertion>` and the signed `<SignedInfo>`
  identically. `xml_text/1` applied to base64 digest/signature values is a
  provable no-op (base64 alphabet has no XML metacharacters).
- **Attribute vs text escaping is correctly differentiated** —
  `AttributeEscape.escape_attribute/1` for attributes (escapes `"`, tabs,
  newlines), `xml_text/1` for element text. Verified against the prod-compiled
  `AttributeEscape` source.
- **The bounded inflate loop is leak-free and fail-closed** — the `after` block
  always closes the zlib port; overflow on either `{:continue, _}` or
  `{:finished, _}` returns `:error`, mapped to `nil` by the caller's `with/else`.
- **NCName ID regex is correctly anchored** — `\b` prevents `ProviderID="…"` /
  `UUID="…"` from being mis-captured (traced: word boundary requires a non-word
  char before `I`, absent in those tokens).
- **The tamper no-op guard is real** — `String.replace` returns the input
  unchanged on no-match, so `tampered == xml` raises descriptively.
- **HEEX auto-escaping** covers `@relay_state` / `@in_response_to` attribute
  interpolations in `login.html.heex` and `@saml_response` in `sso.html.heex`.

No critical defects found. The findings below are robustness and
maintainability concerns appropriate to a demo harness.

## Warnings

### WR-01: `extract_in_response_to/1` grabs the first `ID=` attribute anywhere in the document, not the root element's

**File:** `demo/ledger_loop/lib/ledger_loop_web/controllers/fake_idp_controller.ex:132`
**Issue:** The regex `~r/\bID="([A-Za-z_][A-Za-z0-9._-]*)"/` is run against the
entire inflated XML and returns the **first** match in byte order. The inline
comment asserts "The first ID attribute in a well-formed SP AuthnRequest is the
root AuthnRequest/@ID," but that is an assumption about *well-formed* input, not
an enforced property. A crafted `SAMLRequest` can place an `ID="…"` on a child
element (e.g. `<Issuer ID="x">`) or inject a comment/attribute ordering that
makes a non-root `ID` win. The captured value is NCName-constrained and escaped
downstream (no injection), so impact is limited to threading an attacker-chosen
`InResponseTo` — which on the demo path is cosmetic. Still, the code's stated
contract ("root @ID") is not what the code does.
**Fix:** Either tighten the comment to state the actual behavior ("first
NCName-valued `ID` attribute anywhere in the stream") or anchor the match to the
root element, e.g.:
```elixir
# Match ID only on the document's first start tag (the root element).
with [_, id] <- Regex.run(~r/\A\s*<[^>]*\bID="([A-Za-z_][A-Za-z0-9._-]*)"/, xml) do
  id
end
```

### WR-02: Tamper regex capture group is dead; replacement does not preserve `Format` attribute

**File:** `demo/ledger_loop/lib/ledger_loop/fake_idp/signer.ex:107`
**Issue:** `String.replace(xml, ~r/<NameID[^>]*>([^<]+)<\/NameID>/, "<NameID>TAMPERED</NameID>")`
captures `([^<]+)` but never references it, and the replacement hard-codes
`<NameID>` — dropping any attributes the regex's `[^>]*` matched. The comment
(lines 105-106) explicitly broadened the regex to tolerate
`<NameID Format="…">`, but the replacement then *strips* that `Format`
attribute. Today's live template emits a bare `<NameID>` (signer.ex:163), so the
mutation still produces well-formed XML and the digest still mismatches — the
test passes. But the broadening is self-defeating: if the template ever gains a
`<NameID Format="…">`, the tamper output silently loses the attribute, which
could shift *which* validation step rejects (the stated goal was to keep
rejection at the crypto gate, not an earlier protocol step). The dead capture
group signals the intent was to preserve surrounding shape.
**Fix:** Preserve the original open tag so only the text is mutated, making the
broadened regex actually meaningful:
```elixir
tampered = String.replace(xml, ~r/(<NameID[^>]*>)[^<]+(<\/NameID>)/, "\\1TAMPERED\\2")
```

### WR-03: `signed_response/1` emits `InResponseTo=""` when caller passes `nil`, which a strict SP would reject

**File:** `demo/ledger_loop/lib/ledger_loop/fake_idp/signer.ex:128,157`
**Issue:** `build_fields/1` requires `:in_response_to` via `Keyword.fetch!`, but
the controller's `sso/2` passes `in_response_to: params["in_response_to"]`,
which is `nil` on a direct (non-SP-initiated) visit. `response_xml/3` then emits
`InResponseTo=""`. An empty `InResponseTo` is not the same as an absent one;
a strict SP (including Relyra on the real ACS path) may reject `InResponseTo=""`
as a malformed correlation, producing a confusing "failure" that looks like a
signing bug rather than a missing-correlation condition. Because this is the
demo's success path, a silent empty attribute degrades the harness's diagnostic
value.
**Fix:** Omit the `InResponseTo` attribute entirely when the value is nil/empty,
rather than emitting an empty string:
```elixir
in_response_to_attr =
  case fields.in_response_to do
    nil -> ""
    "" -> ""
    v -> ~s( InResponseTo="#{AttributeEscape.escape_attribute(v)}")
  end
# ...
"<Response Destination=\"...\"#{in_response_to_attr} ConnectionId=\"valid\">"
```
Alternatively, document that direct visits intentionally emit `InResponseTo=""`
and confirm Relyra tolerates it.

## Info

### IN-01: `xml_text(nil)` clause is unreachable

**File:** `demo/ledger_loop/lib/ledger_loop/fake_idp/signer.ex:196`
**Issue:** `xml_text/1` has a `nil` clause, but every call site passes either a
`fetch!`-required field (always a binary) or a base64 string. The only nullable
field, `in_response_to`, flows through `AttributeEscape.escape_attribute` (not
`xml_text`). The clause is dead. It's harmless defensive code, but it can give a
false impression that some text node is nullable.
**Fix:** Remove the `xml_text(nil)` clause, or add a comment noting it is purely
defensive.

### IN-02: Hardcoded ACS path uses string interpolation instead of route helper

**File:** `demo/ledger_loop/lib/ledger_loop_web/controllers/fake_idp_controller.ex:79`
**Issue:** `acs_url = "/saml/#{conn_ulid}/acs"` hand-builds the ACS path. If the
router path for the ACS endpoint ever changes, this silently drifts and the
self-submitting POST 404s. Acceptable for a demo, but a verified route helper
would catch drift at compile time.
**Fix:** Use the generated route helper (e.g. `~p"/saml/#{conn_ulid}/acs"` with
verified routes) so a router change is caught by the compiler.

### IN-03: Dead `compressed` binding in test fixture

**File:** `demo/ledger_loop/test/ledger_loop_web/controllers/fake_idp_controller_test.exs:16,25`
**Issue:** `compressed = :zlib.compress(large_payload)` followed by
`_ = compressed` is dead — the fixture re-compresses with raw deflate on lines
22-24 and only uses `raw_deflated`. The zlib-wrapped `compressed` value is
computed and discarded, adding noise and a misleading suggestion that both
encodings matter.
**Fix:** Delete lines 16 and 25 (`compressed = …` and `_ = compressed`).

### IN-04: `private_key/0` cache persists across the whole VM with no invalidation hook

**File:** `demo/ledger_loop/lib/ledger_loop/fake_idp/keypair.ex:24-34`
**Issue:** The key is cached in `:persistent_term` keyed by `{__MODULE__,
:private_key}` with no eviction path. For a demo this is fine, but
`:persistent_term.put/2` triggers a global GC scan and the value lives for the
VM lifetime; tests that might want to swap the key fixture cannot. Low impact
given the key never changes at runtime.
**Fix:** None required for demo scope. If test flexibility is ever needed, expose
a `reset_cache/0` helper that calls `:persistent_term.erase/1`.
