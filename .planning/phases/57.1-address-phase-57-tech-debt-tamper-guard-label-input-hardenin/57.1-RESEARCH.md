### Pattern 1: Escape at emission, not at ingest

**What:** Escape interpolated values inside `response_xml/3` at the moment of string interpolation.
**When to use:** Whenever untrusted (or even trusted-but-stringly-typed) values flow into a
hand-built XML string.
**Why it is safe for the digest path:** The signer re-parses its **own emitted XML** through
`SaxyTree.parse` and computes the digest over the canonicalized bytes of that parse
(`PureBeam.canonicalize`). Escaping happens once, in `response_xml/3`, *before* parsing. The parser
un-escapes entities back to their character values when it builds the tree, and C14N re-escapes
canonically. Because escaping is applied uniformly across all three `response_xml/3` calls
(placeholder, digest, signed), the digest is computed over the same logical content every time — the
escaping cannot desync the digest. `[VERIFIED: signer.ex:65-84 — three response_xml/3 calls; digest over re-parsed Assertion node]`

### Pattern 2: Bounded inflate with fail-closed-to-nil

**What:** Loop `:zlib.safeInflate/2`, accumulate output, abort when accumulated bytes exceed the
ceiling, and on any abort/error return `:error` from `inflate/1` so the existing `with` chain in
`extract_in_response_to/1` collapses to `nil`.
**When to use:** Decompressing any browser-supplied bytes.
**Contract preservation:** `extract_in_response_to/1` already returns `nil` on any failure
(`else -> nil`). Overflow must route through that same `:error` → `nil` path, NOT introduce a raise
or a new return shape. `[VERIFIED: fake_idp_controller.ex:114-124]`

### Pattern 3: Detectable no-op (raise) for safety helpers

**What:** A helper whose entire purpose is to mutate must assert it actually mutated.
**When to use:** `tamper/1` — if the regex fails to match, the "tampered" Response would be a valid
signed Response and the rejection proof would silently pass. Raise instead.

### Anti-Patterns to Avoid

- **Capping only compressed-input length** and calling it "bounded inflate" — does not bound the
  amplification ratio. Bound the *output*.
- **Adding a new error mode to `inflate/1`** (e.g. raising on overflow) — breaks the "garbled → nil"
  contract. Return `:error`.
- **Escaping in only one of the three `response_xml/3` call sites** — they share one function, so this
  is a non-issue *as long as* escaping lives inside `response_xml/3` itself. Do not escape at the
  call sites in `signed_response/1`.
- **Editing anything under `lib/relyra/`** — out of scope; the verifier gate is sacrosanct.
- **Inventing a new seeded subject for WR-02** — explicitly forbidden by CONTEXT; relabel to the
  existing `sarah@northstar.example.com`.

## Common Pitfalls

### Pitfall 1: Escaping breaks the digest because it is applied inconsistently
**What goes wrong:** Escaping applied at the call site of one of the three `response_xml/3` invocations
but not the others → the placeholder/digest/signed XML differ in escaping → digest computed over
different bytes than the verifier sees.
**Why it happens:** Misreading the signer's 3-pass structure (`signed_response/1` calls
`response_xml/3` three times: placeholder, digest, signed).
**How to avoid:** Apply escaping **inside `response_xml/3`** only. All three passes then share identical
escaping. `[VERIFIED: signer.ex:65,77,83]`
**Warning signs:** `signer_test.exs` "produces a base64 SAMLResponse that Relyra.Security.Signature.verify/4
accepts" starts failing with `:digest_mismatch`.

### Pitfall 2: `safeInflate` loop never terminates on a truncated stream
**What goes wrong:** A crafted stream that returns `{:continue, _}` forever or errors mid-stream.
**Why it happens:** Not handling the `{:continue, _}` vs `{:finished, _}` distinction, or not wrapping
in the existing `try/rescue`.
**How to avoid:** The loop has two exits: (a) accumulated bytes exceed the ceiling → return `:error`;
(b) `safeInflate` raises on a malformed stream → caught by `rescue _ -> :error`. Keep the existing
`try/rescue/after` shape that closes the zlib port. `[VERIFIED: fake_idp_controller.ex:126-139]`
**Warning signs:** A test feeding a >64 KiB-inflating input hangs instead of returning `nil`.

### Pitfall 3: Tamper guard fires today (false positive) because the broadened regex is wrong
**What goes wrong:** Broadening to `<NameID[^>]*>` but the replacement string still emits `<NameID>`
(no attrs), so on a future templated `<NameID Format="…">` the bytes *do* change but to a structurally
different tag. For *today's* template (`<NameID>sarah@…</NameID>`) the replacement must still change
the bytes (sarah@… → TAMPERED), so the guard must NOT raise now.
**Why it happens:** Confusing "match broadened" with "replacement broadened."
**How to avoid:** Keep the replacement `<NameID>TAMPERED</NameID>` (the review's exact snippet). The
regression test must assert tampering today's output *still changes bytes* (guard does not fire) AND
that handing the helper XML with no `<NameID>` raises. `[CITED: 57-REVIEW.md WR-05 fix snippet]`
**Warning signs:** The existing `tamper/1` tests in `signer_test.exs:71-93` raise.

### Pitfall 4: Tightened ID regex rejects the real AuthnRequest ID
**What goes wrong:** Over-tight NCName regex rejects valid SP-generated IDs (e.g. relyra's own
`AuthnRequest` IDs), breaking the success round-trip in `fake_idp_flow_test.exs`.
**Why it happens:** xsd:ID values are NCNames — they start with a letter or `_`, then letters, digits,
`.`, `-`, `_`. Relyra's binding generates IDs like `_<hex>` or `id-<...>`. A regex that forbids `-` or
the leading `_` would reject them.
**How to avoid:** Use the full NCName grammar (see Code Examples) and verify against an actual
relyra-emitted `SAMLRequest` ID via the existing flow test. `[VERIFIED: fake_idp_flow_test.exs:45-70 exercises the real binding ID]`
**Warning signs:** `fake_idp_flow_test.exs` SUCCESS round-trip loses its `in_response_to` (→ nil).

## Code Examples

### WR-04 — bounded inflate (`:zlib.safeInflate/2`, fail closed to nil)

```elixir
# Source: OTP 28 :zlib.safeInflate/2 (confirmed exported). Replaces the single-shot
# :zlib.inflate/2 at fake_idp_controller.ex:126-139. Keeps the try/rescue/after shape
# and the {:ok, bin} | :error contract that extract_in_response_to/1 already expects.

@max_inflated_bytes 64 * 1024  # 64 KiB — generous for a SAML AuthnRequest (typically <4 KiB)

defp inflate(compressed) do
  z = :zlib.open()

  try do
    :ok = :zlib.inflateInit(z, -15)        # raw inflate, mirrors Binding.deflate_xml/1
    inflate_loop(z, compressed, [], 0)
  rescue
    _ -> :error
  after
    :zlib.close(z)
  end
end

defp inflate_loop(z, input, acc, total) do
  case :zlib.safeInflate(z, input) do
    {:continue, output} ->
      chunk = IO.iodata_to_binary(output)
      total = total + byte_size(chunk)
      if total > @max_inflated_bytes do
        :error                              # overflow → fail closed → caller maps to nil
      else
        # subsequent calls feed [] to drain the same stream
        inflate_loop(z, [], [chunk | acc], total)
      end

    {:finished, output} ->
      chunk = IO.iodata_to_binary(output)
      total = total + byte_size(chunk)
      if total > @max_inflated_bytes do
        :error
      else
        {:ok, IO.iodata_to_binary(Enum.reverse([chunk | acc]))}
      end
  end
end
```

> Note for the planner: confirm the exact `safeInflate` drain idiom (feeding `[]` on continuation) at
> implementation time against the OTP 28 docs/behaviour — the byte-ceiling logic and the `:error`→`nil`
> contract are the load-bearing parts. A simpler accepted variant: one `safeInflate(z, compressed)`
> call followed by `safeInflate(z, [])` until `{:finished, _}`, capping the accumulator each iteration.

### WR-01 — escape in `response_xml/3`

```elixir
# Attributes: reuse the prod util. Element text: tiny local helper (AttributeEscape does
# not escape ">" and over-escapes whitespace, which is wrong for text nodes).
alias Relyra.Security.XML.AttributeEscape

defp xml_text(value) when is_binary(value) do
  value
  |> String.replace("&", "&amp;")
  |> String.replace("<", "&lt;")
  |> String.replace(">", "&gt;")
end
defp xml_text(nil), do: ""

# in response_xml/3 — attributes via AttributeEscape, element text via xml_text:
"<Response Destination=\"#{AttributeEscape.escape_attribute(fields.destination)}\" " <>
  "InResponseTo=\"#{AttributeEscape.escape_attribute(fields.in_response_to || "")}\" ConnectionId=\"valid\">" <>
  "<Issuer>#{xml_text(fields.issuer)}</Issuer>" <>

```

> (`signer.ex:65,77,83`) escape identically → the digest is stable. `digest_value_b64` and
> `signature_value_b64` are base64 (no XML metacharacters) so they need no escaping, but uniform
> `xml_text/1` on them is harmless.

### WR-05 — tamper guard + raise on no-op

```elixir
# signer.ex tamper/1 (replaces lines 102-106).
def tamper(b64) when is_binary(b64) do
  xml = Base.decode64!(b64)
  tampered = String.replace(xml, ~r/<NameID[^>]*>([^<]+)<\/NameID>/, "<NameID>TAMPERED</NameID>")

  if tampered == xml do
    raise "tamper/1 failed to locate <NameID>; template drifted"
  end

  Base.encode64(tampered)
end
```

# fake_idp_controller.ex extract_in_response_to/1 — tighten the capture to the xsd:ID / NCName

## Security Domain

`security_enforcement` is not disabled. This phase IS input-hardening, so the security lens is central
— but the trust boundary is the demo FakeIdP's unauthenticated endpoints, NOT the Relyra verifier
(which is untouched).

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | no | FakeIdP is a deliberately-labelled test harness; the real auth gate is Relyra's verifier (out of scope) |
| V3 Session Management | no | unchanged |
| V4 Access Control | no | unchanged |
| V5 Input Validation | **yes** | WR-01 (XML escaping), WR-03 (unknown-action catch-all), WR-04 (bounded inflate), IN-03 (NCName grammar) — all input-validation/output-encoding controls on the FakeIdP boundary |
| V6 Cryptography | no (do-not-touch) | The signer's crypto path is unchanged; the anti-divergence guarantee and `do_verify/4` gate stay intact |
| V12/V13 (Files/API DoS) | **yes** | WR-04 decompression-bomb mitigation on an unauthenticated GET handler |

### Known Threat Patterns for the FakeIdP boundary

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| XML injection via raw `InResponseTo` interpolation | Tampering | Output-encode all interpolated values (WR-01) + NCName input validation (IN-03) |
| Decompression bomb (zip-bomb amplification) | Denial of Service | Bounded `:zlib.safeInflate/2` with output ceiling, fail closed to `nil` (WR-04) |
| Unhandled-input crash via crafted `idp_action` | Denial of Service | Catch-all `case` clause, fail to success path (WR-03) |
| Silent-no-op tamper (false-negative rejection proof) | Repudiation / integrity-of-test | Raise on no-op so the rejection proof cannot pass spuriously (WR-05) |
| Opaque PEM MatchError | (diagnosability) | Typed match + descriptive raise (IN-02) |

**Invariant check:** None of these mitigations touch the six CLAUDE.md non-negotiable invariants. The
verifier still trusts only configured IdP certs, parses once, recomputes the digest, and verifies the
signature. The demo escaping is applied *before* the signer re-parses its own output, so the digest
path is unaffected.
