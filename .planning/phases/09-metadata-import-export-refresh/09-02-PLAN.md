  <action>Create `Relyra.Ecto.MetadataApply.apply_revision/4` plus a dedicated pre-apply attempt writer such as `record_attempt/4` in the same module. Follow the tuple/error normalization, repo-option validation, and record-fetch posture mapped in `09-PATTERNS.md` from `lib/relyra/ecto/connections.ex`, and mirror the certificate association/update contract from `lib/relyra/ecto/certificate.ex`. `apply_revision/4` should accept `connection_id`, a normalized metadata candidate struct/map, revision attributes, and `repo: ...`. `record_attempt/4` should accept revision attributes for malformed XML, validation failures, and remote-fetch failures and persist a durable metadata revision row with `source_kind`, `trigger`, `actor`, `cause`, `outcome`, optional `content_hash_sha256`, and redaction-safe `details` without mutating connection rows or certificate inventory. Implement the D-02 two-boundary split: `apply_revision/4` performs the live apply boundary only after fetch/parse/normalize/validate succeeded, while `record_attempt/4` satisfies D-18 for failed attempts that never reach live apply. Keep those boundaries intentionally separable for D-05: candidate evaluation and revision persistence must be callable without immediately executing live apply, so a future diff-preview or approval-queue slice can insert itself between candidate creation and `apply_revision/4` without changing resolver reads, pointer semantics, or certificate-apply mechanics. Preserve compatibility with the shared \"Provider defaults after normalization\" pattern called out in `09-PATTERNS.md`: apply-time shaping must not bypass the same provider-default expansion and canonical `idp_certificates` runtime expectations that `Relyra.Ecto.ConnectionSnapshot` and `Relyra.Provider` already establish. Use one `Repo.transact/2` boundary inside `apply_revision/4` to: load the current connection plus certificates, insert the metadata revision row first, replace or upsert certificate inventory from the candidate certificate list using `source: \"metadata_revision:<revision_id>\"`, update live connection fields (`idp_entity_id`, `idp_sso_url`) and both pointer columns, and preserve the previous last-known-good pointer when the new revision outcome is not `:applied`. On successful apply, set both pointers to the new revision if there was no prior good revision; otherwise keep `last_known_good_metadata_revision_id` aligned to the newest successfully applied revision. Normalize failures to `%Relyra.Error{}` tuples like existing Ecto write APIs. Do not mutate `Relyra.Ecto.ConnectionLoader` or `Relyra.Ecto.ConnectionSnapshot`; Phase 08 runtime resolution must remain aggregate-only and snapshot-first.</action>
