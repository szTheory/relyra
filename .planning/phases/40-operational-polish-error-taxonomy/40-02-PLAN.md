operator path is grep-the-source — which defeats the strict-defaults posture of the
library.

Six scenarios (D-15), each Triage → Diagnose → Recover, cross-referencing the surface table:

  Scenario 1 — Certificate expiry imminent:
    Symptom: (no atom; warning-only via telemetry).
    Triage:   [:relyra, :saml, :certificate, :expiring] telemetry event fired.
    Diagnose: /relyra/admin/connections/:connection_id (cert inventory section);
              audit ledger query: domain=:certificate action in [:staged, :activated].
    Recover:  staged cert rollover via the admin UI; mix relyra.refresh_due if a
              new IdP metadata fetch is needed.

  Scenario 2 — Metadata drift after IdP change:
    Symptom atom: :metadata_drift_requires_review.
    Triage:   [:relyra, :saml, :metadata, :auto_refresh, :degraded] or :suspended
              telemetry; audit row domain=:metadata action=:applied with drift flag.
    Diagnose: /relyra/admin/connections/:connection_id/metadata (review the drift);
              audit ledger query: domain=:metadata action in [:applied, :refreshed].
    Recover:  mix relyra.refresh_due, then approve drift via admin UI or
              mix relyra.metadata.pin if a hard fingerprint is needed.

  Scenario 3 — Replay storm (NO audit signal — explicit callout):
    Symptom atom: :replayed_assertion.
    Triage:   [:relyra, :saml, :replay, :check] telemetry showing repeated
              :stop with :result == :replayed (telemetry is the ONLY signal —
              replays do not mutate trust state, so no audit row is written
              by lib/relyra/replay_store/{ecto,ets}.ex — verified RESEARCH.md
              Step 4).
    Diagnose: Volume / source-IP analysis from host log infrastructure; no
              admin LiveView surface exists for replay activity (Phase 40 does
              not add one; see Deferred Ideas in CONTEXT.md).
    Recover:  Host-app-level rate limiting on the ACS endpoint; if the storm
              correlates with a single connection, disable the connection
              via /relyra/admin/connections/:connection_id/edit.

  Scenario 4 — Signature regression after IdP key rotation:
    Symptom atoms: :digest_mismatch, :invalid_signature, :trust_anchor_mismatch.
    Triage:   [:relyra, :saml, :signature, :verify] telemetry :stop with
              :result :error and the atom; correlate against the connection_id.
    Diagnose: /relyra/admin/connections/:connection_id (signing cert inventory);
              mix relyra.diagnostic to bundle the connection + the failing
              response payload for IdP support; cross-link to
              ../troubleshooting.md#digest_mismatch and #trust_anchor_mismatch.
    Recover:  Stage the new IdP signing cert via the admin UI (cert inventory
              :staged → :activated); confirm the next login succeeds; retire
              the old cert (audit row domain=:certificate action=:retired).

  Scenario 5 — ACS misconfiguration at provisioning:
    Symptom atoms: :destination_mismatch, :recipient_mismatch, :in_response_to_mismatch.
    Triage:   [:relyra, :saml, :response, :validate] telemetry :stop with
              :result :error; the atom names which exact field mismatched.
    Diagnose: /relyra/admin/connections/:connection_id/edit — verify acs_url,
              sp_entity_id, idp_entity_id, idp_sso_url match the IdP's
              published metadata; cross-link to ../troubleshooting.md#destination_mismatch.
    Recover:  Update the connection field via the admin UI; audit row
              domain=:connection action=:updated will record the change.

  Scenario 6 — Attribute mapping breakage:
    Symptom atom: :invalid_audience (and related; mapping atoms can surface as
                  identity-mapping errors at the host-app boundary).
    Triage:   [:relyra, :saml, :user, :map] telemetry showing the failure;
              audit ledger query: domain=:mapping action in [:created, :updated].
    Diagnose: /relyra/admin/connections/:connection_id (mapping section + audit
              timeline); cross-link to ../troubleshooting.md#invalid_audience.
    Recover:  Update the mapping via the admin UI (or via the
              UserMapper implementation in the host app — see
              guides/identity_mapping_and_provisioning.md).
