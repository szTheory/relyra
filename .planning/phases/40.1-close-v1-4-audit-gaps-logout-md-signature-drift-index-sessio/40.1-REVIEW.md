## Summary

Phase 40.1 closes the BLOCKER 1 / DOCS-04 signature drift from
`v1.4-MILESTONE-AUDIT.md` by rewriting the `SessionAdapter` example in
`guides/recipes/logout.md` to canonical 4-arg signatures, adding a
host-owned linkage clarification (closes the SLO-01 integration gap), and
landing a runtime-introspected drift gate (`test/docs/logout_recipe_drift_test.exs`)
wired into `ci.docs` as its own dedicated `cmd mix test` line.

The core fix is sound — the example signatures now match
`Relyra.SessionAdapter.behaviour_info(:callbacks)` exactly, the
`context`/`session_index` story aligns with what `lib/relyra.ex`
`handle_idp_initiated_logout` actually passes to the adapter
(`%{connection_id: ...}`), and the new drift test will catch future
arity drift via runtime introspection per D-05.

Three real concerns surfaced:

1. **WR-01 (drift test brittleness): a single literal `def name(...)`
   anywhere in `logout.md` outside the example code fence will trip the
   gate** — there's no fenced-block scoping, so the regex is one prose
   accident away from a false positive or false negative.
2. **WR-02: the example teaches hosts to emit two undocumented error
   atoms** (`:session_index_store_failed`, `:session_terminate_failed`)
   that have zero presence in `lib/` and zero decoder entries in
   `guides/troubleshooting.md`. Hosts copy-pasting the example would
   immediately produce error atoms with no operator vocabulary — this
   undermines DOCS-06 and the whole troubleshooting decoder.
3. **WR-03: `count_params/1` mis-counts realistic Elixir parameter
   syntax** — defaults (`opts \\ []`), tuples/maps/lists in pattern
   match (`{a, b}`, `[h | t]`, `%{a: 1}`), and keyword-style options
   all break a naive comma split. The current example survives because
   it uses only bare atoms, but the gate will produce confusing
   failures if a future doc author makes the example more realistic.

Info items cover doc-structure fallow findings outside this commit's
diff but inside the file under review (three consecutive H2 headings),
the cwd-relative path already flagged by Phase 40 WR-02, and the
unrelated bare-`test`-after-bare-`test` pair on lines 162-163 of
`mix.exs` that the test moduledoc obliquely concedes ("by convention
rather than by gate"). None are blockers.

## Warnings

### WR-01: drift test regex matches any `def index_session(...)` anywhere in `logout.md`, not just inside the fenced code block

**File:** `test/docs/logout_recipe_drift_test.exs:62`
**Issue:** `@head_pattern ~r/^\s*def\s+(index_session|terminate_by_session_index)\s*\(([^)]*)\)/m`
is applied to the entire file body with no code-fence scoping. If a
future doc author writes prose like

```text
You can use `def index_session(connection, login_result, local_session_id, opts)`
in your callback module ...
```

at the start of a line (after expansion of leading list markers,
quoted code-block prose, etc.), the regex captures it as a real
example head and the arity-parity assertion trips on 4 vs 4 (OK now)
or 5 vs 4 (false positive failure) depending on what the prose says.
The inverse is worse: a docs refactor that moves the example into a
section title, an attribute table, or an `### ` heading line that
happens not to start with `def` produces a false negative — the
coverage assertion fires "missing doc example" even though the doc
clearly documents the callback in another form. Compare to the
troubleshooting drift gate (`test/docs/troubleshooting_drift_test.exs`),
which is similarly unscoped but operates on a much narrower atom
vocabulary — the SessionAdapter callbacks are more likely to be
mentioned in prose than `:atom`-style error names.

**Fix:** Scope the scan to fenced Elixir code blocks. Two practical
options:

```elixir
# Option A: split on triple-backtick fences, only scan elixir blocks
defp extract_elixir_blocks(doc) do
  ~r/```elixir\n(.*?)```/s
  |> Regex.scan(doc, capture: :all_but_first)
  |> Enum.map_join("\n", fn [body] -> body end)
end

# then:
heads = doc |> extract_elixir_blocks() |> then(&Regex.scan(@head_pattern, &1, capture: :all_but_first))
```

```elixir
# Option B: tighten the head pattern to require the @impl true line above
@head_pattern ~r/@impl true\n\s*def\s+(index_session|terminate_by_session_index)\s*\(([^)]*)\)/m
```

Option A is more robust; Option B is the one-liner. Either prevents
prose drift from corrupting the gate.

### WR-02: example emits two error atoms that exist nowhere in the codebase and have no entry in the SAML Error Atom Decoder

**File:** `guides/recipes/logout.md:123`, `guides/recipes/logout.md:135`
**Issue:** The rewritten example introduces
`Relyra.Error.new(:session_index_store_failed, ...)` and
`Relyra.Error.new(:session_terminate_failed, ...)`. Neither atom is
emitted from `lib/` (`grep -rn "session_index_store_failed\|session_terminate_failed" lib/` returns zero hits) and neither has
a `### :atom` entry in `guides/troubleshooting.md`. A host who
copy-pastes the example (the whole point of a recipe) will emit
typed rejections that:

  1. Have no documented operator decoder entry — violates the spirit
     of DOCS-06 (the canonical operator vocabulary contract).
  2. Are not part of Relyra's typed-error taxonomy — the host's audit
     log will carry atoms that look like Relyra atoms but aren't.
  3. Won't be caught by `troubleshooting_drift_test.exs` because that
     test scans only `lib/**/*.ex`, not `guides/`.

The example essentially invents two new atoms in the SP-library's
namespace and hands them to hosts.

**Fix:** Either (a) demonstrate a host-namespaced atom so it's clear
the host owns the error type:

```elixir
{:error, reason} -> {:error, Relyra.Error.new(:host_session_index_store_failed, inspect(reason))}
```

paired with a one-line comment explicitly noting "host-namespaced error
type — pick your own, Relyra reserves the typed atoms documented in
guides/troubleshooting.md"; or (b) promote both atoms into Relyra's
real taxonomy (add `### :session_index_store_failed` /
`### :session_terminate_failed` H3 entries in `troubleshooting.md`,
and emit them once from `lib/` so the troubleshooting drift gate
covers them). Option (a) is the lighter touch and matches the
host-owned framing the new "Host-owned linkage" H3 is already
establishing.

### WR-03: `count_params/1` is naive — defaults, tuples, lists, maps, and pinned/guarded params all break the comma split

**File:** `test/docs/logout_recipe_drift_test.exs:104-110`
**Issue:** The helper does `String.split(params_string, ",")` then
trims and counts non-empties. This silently mis-counts every
non-trivial Elixir parameter form:

  - `def f(a \\ [])` — `a \\ []` is one parameter, but if the default is
    `[1, 2]` the split produces `["a \\ [1", "2]"]` → returns 2.
  - `def f({k, v}, opts)` — split returns `["{k", "v}", "opts"]` → 3
    (actual: 2).
  - `def f(%{a: 1, b: 2}, opts)` — split returns 3 (actual: 2).
  - `def f([h | t], opts)` — fine for this one, but `[a, b | t]`
    returns 3 (actual: 2).

The current example survives because both heads use only bare atom
parameters separated by commas (`session_index, issuer, context, _opts`).
A future doc author who writes a more realistic example using a map
context literal or a default opts arg would trip the gate with
"arity drift" even though the real arity is correct.

**Fix:** Use Elixir's actual parser instead of a regex/string split.
`Code.string_to_quoted/1` on `"def #{head}(#{params}) do :ok end"`
yields an AST where the `def`'s arg-list length is the true arity.
Sketch:

```elixir
defp count_params(params_string) do
  src = "fn(#{params_string}) -> :ok end"

  case Code.string_to_quoted(src) do
    {:ok, {:fn, _, [{:->, _, [args, _body]}]}} -> length(args)
    {:error, _} -> raise "unparseable params: #{inspect(params_string)}"
  end
end
```

This makes the gate honest for any Elixir-legal param syntax and
fails loudly (rather than silently producing the wrong arity) on
truly broken examples.

### IN-04: drift test asserts on signature, never on body — semantic drift in the example body is invisible

**File:** `test/docs/logout_recipe_drift_test.exs:65-98`
**Issue:** The test verifies callback names exist and parameter
counts match. It does not verify the example body is sane (e.g., the
example could regress to calling `context.foo` where `foo` doesn't
exist, or returning `:ok` instead of `{:ok, _}` and `{:error, _}`).
This is consistent with what the test's moduledoc claims to do, so
it's not a defect — but a future maintainer reading the gate name
"drift test" might assume more coverage than the gate provides. The
moduledoc could be clearer on this scope ceiling.
**Fix:** Add one sentence to the moduledoc: "This gate covers
signature drift only — it does NOT verify the example body returns
the typed `{:ok, _} | {:error, %Relyra.Error{}}` shape the callback
spec mandates. Body correctness is the reviewer's responsibility."
