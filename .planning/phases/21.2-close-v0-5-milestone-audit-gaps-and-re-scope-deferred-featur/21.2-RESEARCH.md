- **Enable** — Move every selected connection to the `enabled` lifecycle state. Each connection's trust change co-commits its own audit row inside its own transaction.
- **Disable** — Move every selected connection to the `disabled` lifecycle state. Existing application sessions are not revoked.
- **Refresh Metadata** — Re-fetch metadata for every selected connection from its registered remote source. The bulk path uses the same operator-triggered manual refresh seam as a single-connection refresh; new signing certificates stage as `:next` rather than promoting implicitly.

Bulk actions execute sequentially (one connection at a time) to keep database pressure bounded and audit ordering explicit. The aggregate flash message reports per-connection success and failure counts; partial failures do not abort the batch.

Audit trail: every per-connection row in a bulk run shares the bulk `correlation_id` and the operator-attributed `actor` / `cause`, so an operator reviewing the audit ledger can reconstruct "who ran which bulk action across which connections" from a single shared identifier.

The seam is `Relyra.Ecto.BulkActions.run/4`. Hosts that want to drive bulk actions from a Mix task, a script, or a custom admin UI can call it directly with a list of `connection_id` values and one of the three action functions:

\```elixir
Relyra.Ecto.BulkActions.run(
  MyApp.Repo,
  ["01JT...", "01JT...", "01JT..."],
  &Relyra.Metadata.refresh/2,
  audit: %{actor: "ops@example.com", cause: "scripted_bulk_refresh"}
)
\```

Returns `{:ok, %{connection_id => {:ok, _} | {:error, %Relyra.Error{}}}}`. The `correlation_id` is auto-generated if not supplied in the audit map.
```

## Common Pitfalls

### Pitfall 1: Partial re-scope (the original audit gap)
**What goes wrong:** Updating PROJECT.md but forgetting REQUIREMENTS.md, or vice versa.
**Why it happens:** The 3-way doc invariant is implicit; a planner who reads only one of CONTEXT.md's "in scope" items can land a partial fix.
**How to avoid:** Run the cross-doc coherence greps (see `## Cross-Doc Coherence Invariants`) post-merge as the phase verification gate. CONTEXT.md `<code_context>` line 140 already flags this: "These three docs must move together for the re-scope to be coherent. A planner that updates one and skips another reintroduces drift."
**Warning signs:** `grep -l "DIAG-01" .planning/{PROJECT,REQUIREMENTS,MILESTONE-ARC}.md` returns fewer than 3 file matches.

### Pitfall 2: README brand-voice drift
**What goes wrong:** The new bulk-actions subsection uses banned terms (`polling`, `cron job`, etc.) that pass casual human review but trip the LiveView grep tests' spirit.
**Why it happens:** No automated test enforces brand voice on README content (verified — no `grep -rln "README" /Users/jon/projects/relyra/test`). The constraint is convention-only.
**How to avoid:** Apply the same banned-term lint manually during plan-checker review. The grep-verifiable acceptance criterion in `## Cross-Doc Coherence Invariants` (row "README does NOT use brand-banned terms") catches this in CI-equivalent verification.
**Warning signs:** `awk` slice of the new section grep-matches any banned term.

### Pitfall 3: Editing the wrong doc footer
**What goes wrong:** Updating MILESTONE-ARC.md's `*Last updated*` line directly (deleting the prior text) instead of appending a new annotation above it.
**Why it happens:** The doc's own rule (line 68) is in prose, not enforced; "annotate, don't delete" requires careful reading.
**How to avoid:** Quote the rule into the plan's `<read_first>` block. Acceptance criterion: `grep -c "Last updated" .planning/MILESTONE-ARC.md` after the edit MUST equal `1` (the original line is preserved); the NEW annotation is a separate `*2026-05-07 — ...*` line above it.
**Warning signs:** Any check that compares pre/post line counts of MILESTONE-ARC.md showing the file got SHORTER instead of longer.

### Pitfall 4: Stale `mix format` drift breaking commits
**What goes wrong:** A doc-only commit triggers a pre-commit hook that runs `mix format --check-formatted` over the codebase and surfaces the pre-existing format drift in `lib/relyra/live_admin/connections_live.ex` (logged in `phases/21-…/deferred-items.md`).
**Why it happens:** The drift originates from Phase 20 commit `6e75525` and predates Phase 21. CONTEXT.md `<deferred>` line 161 confirms it's pre-existing.
**How to avoid:** Verified — no pre-commit hook is registered (no `.git/hooks` modification observed in repo state). Doc-only commits will not invoke `mix format`. **No action needed**, but the planner SHOULD verify by running `git config --get core.hooksPath` and `ls .git/hooks/pre-commit*` before the first 21.2 commit.
**Warning signs:** Any commit failure mentioning `mix format` — if observed, halt and surface to operator.

### Pitfall 5: Generating an unnecessary v0.5-REQUIREMENTS.md archive
**What goes wrong:** A planner reads CONTEXT D-21.2-08 ("frontmatter refresh in place v0.4 → v0.5") and instead creates `.planning/milestones/v0.5-REQUIREMENTS.md` thinking it's the canonical v0.5 record.
**Why it happens:** The v0.1/v0.2/v0.3 archives in `.planning/milestones/` look like a parallel pattern.
**How to avoid:** CONTEXT D-21.2-09 is explicit: "Do NOT create `.planning/milestones/v0.5-REQUIREMENTS.md` in this phase. The archive snapshot is produced by `/gsd-complete-milestone v0.5` (matches v0.1/v0.2/v0.3 pattern)." Acceptance criterion: `test ! -f .planning/milestones/v0.5-REQUIREMENTS.md`.
**Warning signs:** The 21.2 commit history references creating a new file under `.planning/milestones/`.

### Pitfall 6: Plan-checker rejecting `requirements: []` frontmatter
**What goes wrong:** The plan-checker enforces "every plan must address its phase's REQ-IDs," but 21.2 has none.
**Why it happens:** The 21.1 plan-checker pattern was tuned against `requirements: [CFG-07]`; an empty list may be treated as a violation by a strict checker.
**How to avoid:** Set `requirements: []` explicitly (NOT omit the key). Add an inline comment in the frontmatter: `# Phase 21.2 has no functional REQ-IDs (doc-only closure phase per CONTEXT.md additional_context)`. If the plan-checker still flags it, escalate to operator — do NOT invent a fake REQ-ID.
**Warning signs:** Plan-checker returns "no requirements coverage" for one or more 21.2 plans.

### Pitfall 7: Auto-advance / commit_docs unintended side-effects
**What goes wrong:** `.planning/config.json` has `commit_docs: true` and `auto_advance: false`. A plan task that creates a doc may auto-commit before the planner's review pass completes.
**Why it happens:** The orchestrator's `commit_docs` flag is a global setting, not per-task.
**How to avoid:** This is the EXPECTED behavior for closure phases (matches 21.1's commit pattern: every 21.1 plan task created its own atomic commit). The planner SHOULD design for atomic commits. If a task needs intermediate state (rare for doc-only), explicit `<commit>false</commit>` in the task XML can override.
**Warning signs:** None — `commit_docs: true` is the desired posture for 21.2.
