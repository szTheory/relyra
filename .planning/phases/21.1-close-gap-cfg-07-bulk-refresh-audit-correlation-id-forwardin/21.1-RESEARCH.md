# Phase 21.1: Close gap CFG-07 — bulk-refresh audit correlation_id forwarding — Research

**Researched:** 2026-05-07
**Domain:** Audit-ledger correlation propagation across the manual `Refresh.refresh/2` path (Phase 9/12) ↔ `BulkActions.run/4` (Phase 20) seam
**Confidence:** HIGH

## Summary

This is a **single-file gap closure**, not exploratory research. The fix shape is fully specified by the audit doc + author-curated CONTEXT.md (D-21.1-01..08). My job was (1) to validate that the fix is genuinely localized to `lib/relyra/metadata/refresh.ex` and there are no sibling sites where the planner could miss a parallel forwarding bug, (2) to specify the Validation Architecture (Nyquist Dimension 8) precisely, and (3) to surface landmines specific to this codebase's test fixtures and audit-row assertion patterns.

**Sibling-site audit (HIGH confidence):** The bug is genuinely scoped to `Refresh.refresh/2` + `record_refresh_failure/7`. Every other `Metadata.refresh`-adjacent caller is either already-correct (`AutoRefresh.refresh/2` forwards `opts` verbatim into `MetadataApply.apply_revision/4`) or never reaches the audit ledger from a bulk path (single-connection LiveView, mix tasks). One adjacent finding worth the planner's awareness: `connection_metadata_live.ex:69-88` and `connections_live.ex:106-131` use the SAME `audit_context/2` helper (`%{actor: scope.actor, cause: cause}` — without `:correlation_id`); the bulk-list path's correlation_id comes ONLY from `BulkActions.run/4`'s auto-injection at `bulk_actions.ex:16-18`. Single-connection refresh has no `:correlation_id` to forward, so D-21.1-03 fallback ordering (top-level keyword opts → defaults) is the regression-guard contract for the non-bulk callers.

**Failure-path semantics (HIGH confidence):** `MetadataApply.record_attempt/3` does NOT write to the audit ledger today. The single-audit-writer-seam invariant (D-35) is enforced numerically — exactly 2 `AuditWriter.append_event` call sites in `metadata_apply.ex` (`apply_revision/4` line 895, `resume_auto_refresh/3` line 250). Both are inside `transact/2` blocks. `record_attempt/3` writes only the `MetadataRevision` row + (when scheduled-trigger) health state. **This means D-21.1-02's "forwarding `audit:` into `record_attempt`" is defensive future-proofing only — it does not change current ledger behavior.** The planner should encode this as "forward `audit:` into `record_attempt` opts; verify no audit-ledger rows are produced on the failure path today; assert this invariant in the test plan as a regression guard for any future seam that adds failure-audit hooks."

**Primary recommendation:** Plan as a 1-task, single-file change in `lib/relyra/metadata/refresh.ex` plus a single new integration-style test file (or extension of the existing `test/relyra/metadata_refresh_test.exs`) that adds (a) the bulk audit-cohesion assertion, (b) the single-connection regression guard, and (c) a failure-path "no audit row" assertion. No schema migration. No public API change. Wave 0 is a no-op (existing test infrastructure covers all phase requirements).

## Failure-Path Semantics (D-21.1-02 clarification)

`MetadataApply.record_attempt/3` (`metadata_apply.ex:74-97`) does the following inside one `transact/2` block:

1. Inserts a `MetadataRevision` row (with the failure outcome, error_code, etc.) — `insert_revision/2`
2. Conditionally updates `MetadataSource` health state — `maybe_update_health_state_on_attempt/2` (gated on `scheduled_trigger?(trigger)` — manual triggers like `:manual_refresh` skip this)
3. **Does NOT call `AuditWriter.append_event`** — verified by grep

Implication: forwarding `audit:` into `record_attempt`'s opts (D-21.1-02) does **not** change current ledger behavior. The forwarded value is propagated:
- Into telemetry payloads via `correlation_id_from_attrs/1` (`metadata_apply.ex:569-580`) — already reads `attrs[:audit][:correlation_id]` and `attrs[:correlation_id]`. Already correct, but gets cleaner data once the planner forwards `audit:` properly.

**Test assertion for the failure path (regression guard):** "After a bulk-refresh failure path runs, the failure connection's `MetadataRevision` row exists, NO `metadata.applied` audit-ledger row exists for that connection (because failure does not call `apply_revision`), and any future `record_attempt`-ledger hook would receive the correctly-forwarded correlation_id." This guards against a future seam being added without re-introducing the gap.

## Architecture Patterns

### System Architecture (Bulk Refresh path — the gap-suffering flow)

```
Operator selects N connections + clicks "Refresh Metadata"
                  │
                  ▼
ConnectionsLive.handle_event("bulk_action", %{"action" => "refresh_metadata"}, socket)
  │  audit = audit_context(scope, "live_admin_bulk_refresh_metadata")  ◄── %{actor:, cause:}
  │
  ▼
BulkActions.run(repo, ids, &Metadata.refresh/2, audit: audit)
  │  correlation_id = audit[:correlation_id] || Ecto.UUID.generate()
  │  opts_with_audit = [..., audit: %{actor:, cause:, correlation_id: <generated>}]
  │
  ▼ (sequential per id, D-38)
Metadata.refresh(connection_id, opts_with_audit)
  │  (thin wrapper validates :repo)
  │
  ▼
Refresh.refresh(connection_id, opts_with_audit)        ◄── ★ THE GAP IS HERE ★
  │  Currently: passes ONLY repo: repo into apply_revision opts
  │  Drops opts[:audit] on the floor
  │
  ▼
MetadataApply.apply_revision(conn_id, candidate, revision_attrs, repo: repo)
  │  audit_context(opts, revision_attrs)  ◄── opts[:audit] is nil; falls through
  │  → audit_context_from_revision/1     ◄── reads actor/cause from revision_attrs
  │     (which Refresh sets from top-level opts[:actor]/opts[:cause]
  │      → "unknown"/"manual refresh" defaults — BulkActions never sets these
  │      at the top level; only inside the audit map.)
  │  correlation_id: Map.get(revision_like, :correlation_id) → nil
  │
  ▼

  │
  ▼

```

### Fix flow (post-Phase-21.1)

```
Refresh.refresh/2 resolves audit context per D-21.1-03:
  audit = case opts[:audit] do
    %{} = a -> Map.merge(%{actor: "unknown", cause: "manual refresh"}, a)
    _ -> %{actor: opts[:actor] || "unknown",
           cause: opts[:cause] || "manual refresh",
           correlation_id: nil}
  end

  MetadataApply.apply_revision(conn_id, candidate, revision_attrs,
                                 repo: repo, audit: audit)  ◄── forward
```

The downstream `audit_context(opts, revision_attrs)` already prefers `opts[:audit]` over `revision_attrs` (`metadata_apply.ex:933-944`), so the forwarded audit map flows straight to `AuditWriter.append_event` — no change required in `MetadataApply`.

### Anti-Patterns to Avoid

- **Hand-rolling correlation_id generation in `Refresh.refresh/2`.** `BulkActions.run/4` and `Scheduler.run_due/2` already inject one. Refresh must FORWARD, not GENERATE — generating one would mask the bug rather than close it (each connection in a bulk run would get a different correlation_id, still violating the cohesion invariant).
- **Adding a third `AuditWriter.append_event` call site.** D-35 invariant is grep-enforced numerically (Plan 21-04 NOTE in STATE.md). Any new audit-writing logic MUST go through `apply_revision/4` or `resume_auto_refresh/3`.
- **Touching `record_attempt/3` to write an audit-ledger row.** Out of scope per CONTEXT.md "Deferred Ideas". Future-failure-audit hooks belong in a different phase.
- **Mutating the `apply_revision/4` public contract.** Already correctly consumes `opts[:audit]`; the bug is upstream.
- **Changing how `connection_metadata_live.ex` calls `Metadata.refresh/2`.** Single-connection callers use top-level `actor:`/`cause:` opts (no `:audit` map); the D-21.1-03 fallback ordering is the regression-guard contract for these callers. Do NOT "fix" them by introducing an `:audit` map on the single-connection path — that is a Phase 21.1+1 concern, not in scope.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| correlation_id generation | New `Ecto.UUID.generate()` call in Refresh | Forward `opts[:audit][:correlation_id]` | `BulkActions`/`Scheduler` already inject one; Refresh's job is to forward |
| Audit-ledger writes from Refresh | Direct `AuditWriter.append_event` call | Trust `MetadataApply.apply_revision/4` to do it via the existing seam | D-35 single-audit-writer-seam invariant |
| Audit-context resolution | Custom `case`/`cond` in Refresh | Forward into `apply_revision`'s already-correct `audit_context/2` helper | `metadata_apply.ex:933-944` already handles map vs. derived from revision_attrs |

**Key insight:** This phase is about **NOT building** anything custom. The downstream consumer is already correct. Refresh's only job is to bridge the keyword-opts → `audit:` map gap that emerged when Phase 20's BulkActions contract was introduced AFTER Refresh was written.

## Common Pitfalls

### Pitfall 1: Generating a fresh correlation_id in Refresh
**What goes wrong:** Each connection in a bulk run gets its own correlation_id; ledger rows look like N independent operations rather than one batch.
**Why it happens:** Easy mistake — "if there's no audit map, just make one." But `BulkActions.run/4` ALWAYS provides one (auto-generates if missing per `bulk_actions.ex:16`).
**How to avoid:** D-21.1-03 fallback ordering MUST treat the absence of `opts[:audit]` as "single-connection caller; no correlation_id needed" — not as "generate one."
**Warning signs:** Test 1 (bulk audit-cohesion) fails with 3 distinct correlation_ids instead of 1.

### Pitfall 2: Test fixture hardcoding correlation_id=nil
**What goes wrong:** Existing `metadata_refresh_test.exs` (single-connection) tests don't assert on the audit-ledger row at all — they only assert revision shape + telemetry. If you accidentally regress the bulk path, single-connection tests will still pass.
**Why it happens:** No existing test queries `AuditEvent` after a `Refresh.refresh/2` invocation. (`grep AuditEvent test/relyra/metadata_refresh_test.exs` returns 0 matches.)
**How to avoid:** Test 1 MUST assert on `AuditEvent` rows (count, correlation_id grouping, actor, cause). Test 2 (single-connection regression guard) MUST assert that the top-level-opts path produces a valid ledger row with the correct actor/cause.
**Warning signs:** Tests pass but a manual `psql -c "SELECT correlation_id, actor, cause FROM relyra_audit_events ORDER BY inserted_at DESC LIMIT 6"` after a bulk action shows distinct correlation_ids.

### Pitfall 3: Sandbox checkout for multi-connection bulk tests
**What goes wrong:** A naive `MigrationCase, async: true` test that inserts 3 connections, then calls `BulkActions.run/4`, can hit `Sandbox.OwnershipError` if the sequential per-id loop somehow forks.
**Why it happens:** `BulkActions.run/4` is sequential (Phase 20 D-38; verified at `bulk_actions.ex:21-25` — plain `Enum.map`, no `Task.async`). So the OwnershipError shouldn't materialize. But the existing `live_admin_bulk_test.exs` uses `async: false` + `Sandbox.start_owner!(@repo, shared: true)` defensively — match that posture.
**How to avoid:** Use `MigrationCase, async: false` (matches `metadata_refresh_test.exs`, `metadata_apply_test.exs`, `bulk_actions_test.exs`-LiveView style). The `MigrationCase`'s `setup` block already calls `Sandbox.start_owner!` and `reset_tables!()`.
**Warning signs:** `Postgrex.Error` or `Sandbox.OwnershipError` mid-test.

### Pitfall 4: Asserting audit-row ORDER under sequential bulk-loop semantics
**What goes wrong:** Bulk test asserts the 3 audit rows in `[:metadata, :applied]` form arrive in `inserted_at` order matching connection input order — but `inserted_at` for rows committed in distinct transactions in microsecond-resolution DB timestamps can collide on fast hardware.
**Why it happens:** Phase 20 uses sequential execution but each connection commits its OWN transaction (the `MetadataRevision` + audit-event co-commit is per-connection; the audit-ledger does NOT see a single batch transaction).
**How to avoid:** Assert on `correlation_id` grouping + count + set-membership of `actor`/`cause`/`subject_ref` (revision IDs), NOT on row ordering. Pattern: `assert events |> Enum.map(& &1.correlation_id) |> Enum.uniq() |> length() == 1`.
**Warning signs:** Test is flaky (passes locally, fails in CI) on `inserted_at`-based assertions.

### Pitfall 5: Assuming `apply_revision/4` overwrites correlation_id from revision_attrs
**What goes wrong:** Planner thinks "I'll just put correlation_id into revision_attrs map" (the audit fix_hint mentions this as one option). But `revision_attrs` is the source for the `MetadataRevision` row's columns, not directly the audit map — the merge happens via `audit_context_from_revision/1` only when `opts[:audit]` is nil.
**Why it happens:** The audit doc's fix_hint says "or merge correlation_id into revision_attrs" — true, but suboptimal. Forwarding into `opts[:audit]` is cleaner and matches the contract `BulkActions` was built for.
**How to avoid:** Use D-21.1-01's "forward `audit:` into `apply_revision` opts" path. The `revision_attrs` route works but creates two ways to populate audit context (the `opts[:audit]` map and the revision-derived path), increasing maintenance surface.
**Warning signs:** Test 2 (single-connection top-level opts) and Test 1 (bulk audit) take different code paths through `audit_context/2` — fragile.

### Pitfall 6: Existing `AuditEvent.cause` is a string column, not an atom
**What goes wrong:** Test asserts `event.cause == :live_admin_bulk_refresh_metadata` and fails because the ledger stores it as `"live_admin_bulk_refresh_metadata"`.
**Why it happens:** `AuditWriter.append_event` accepts string values for `:cause` and `:actor`; `metadata_apply_test.exs:643` reference test asserts `event.actor == "operator-test"` (string).
**How to avoid:** Use string literals in assertions. Match `connections_live.ex:110` which builds `cause: "live_admin_bulk_#{action}"` → `"live_admin_bulk_refresh_metadata"`.
**Warning signs:** Assertion failure with `<> != <>` on quoted strings.
