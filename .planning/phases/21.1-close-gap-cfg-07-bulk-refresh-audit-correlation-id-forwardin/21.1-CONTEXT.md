# Phase 21.1: Close gap CFG-07 — bulk-refresh audit correlation_id forwarding — Context

<domain>
## Phase Boundary

This is a **closure phase** for INT-01 (BLOCKER) raised by `/gsd-audit-milestone v0.5`:

- Bulk `:refresh_metadata` (Phase 20 BulkActions over multiple connections) currently produces
  N audit rows with `correlation_id=nil`, `actor="unknown"`, `cause="manual refresh"`, silently
  violating the Phase 20 batch-cohesion invariant ("one correlation_id per bulk run").
- Asymmetric: `:enable` and `:disable` correctly carry `correlation_id` because
  `Connections.enable/2` accepts `audit:` directly. Only `:refresh_metadata` regresses
  because `Relyra.Metadata.Refresh.refresh/2` predates the bulk-audit contract.

**In scope:**
- Make `Relyra.Metadata.Refresh.refresh/2` forward `opts[:audit]` (correlation_id, actor, cause)
  into `Relyra.Ecto.MetadataApply.apply_revision/4`'s `audit:` opt — both on the success path
  and on the failure path (`record_refresh_failure/7`'s `record_attempt` call).
- Backwards compatibility: continue to honor top-level `opts[:actor]` / `opts[:cause]` for
  callers that do not wrap them in an `audit:` map (single-connection LiveView refresh,
  scheduler `AutoRefresh.refresh/2` wrapper, mix tasks).
- Tests proving:
  - Bulk `:refresh_metadata` over N connections produces N audit rows that share the
    SAME correlation_id (the BulkActions-generated batch id).
  - Bulk audit rows carry the actor/cause from `opts[:audit]`, not the `"unknown"` default.
  - Single-connection refresh (top-level `actor:`/`cause:`) still produces correct audit
    rows (regression guard for non-bulk callers).

**Out of scope (deferred / handled elsewhere):**
- INT-02 README "Operations: Bulk actions" subsection — separate trivial doc fix; not
  blocking for v0.5 closure but tracked in the audit doc.
- Phase 20 retroactive `/gsd-validate-phase 20` — separate cleanup, not gap-closure work.
- Any change to `MetadataApply.apply_revision/4`'s public contract — already correctly
  consumes `opts[:audit]` map; the bug is upstream in `Refresh`.
- Schema changes — none required.

</domain>

<decisions>
## Implementation Decisions

### Source of truth for audit ledger correlation_id semantics
- **D-39 (Phase 21):** Audit row's `correlation_id` is the batch correlation_id when present,
  with the source `Map.get(audit, :correlation_id)` from
  `MetadataApply.apply_revision`'s `audit_context(opts, revision_attrs)` helper at
  `lib/relyra/ecto/metadata_apply.ex:933-944`. This contract is **already correct** —
  the bug is `Refresh` not propagating `audit:` into `apply_revision`'s opts.

### Fix shape (LOCKED — from audit fix_hint)
- **D-21.1-01:** `Refresh.refresh/2` must forward `audit:` from its `opts` keyword list into
  the `MetadataApply.apply_revision/4` call's `opts` keyword list, in addition to `repo:`.
  Single localized change at `lib/relyra/metadata/refresh.ex:52-65`.
- **D-21.1-02:** Same forwarding must apply to the failure path: `record_refresh_failure/7`
  passes `opts` through to `MetadataApply.record_attempt/3`. Although `record_attempt` does
  not currently write the audit ledger (it only inserts the revision attempt + health
  state), the correlation_id should still appear on the inserted revision row when known
  so cross-referencing future ledger writes (e.g., new failure-audit hooks) does not
  regress. (Defensive future-proofing, not a current behavioral change.)
- **D-21.1-03:** Audit-context resolution order in `Refresh.refresh/2` is:
  1. `opts[:audit]` map (preferred — bulk path via BulkActions)
  2. Top-level `opts[:actor]` / `opts[:cause]` (fallback — single-connection callers,
     `AutoRefresh.refresh/2`, mix tasks)
  3. Defaults `actor: "unknown"`, `cause: "manual refresh"` (last resort)

  The forwarded `audit:` map passed to `apply_revision` should always be a single map
  containing `actor`, `cause`, and `correlation_id` (when known), so the downstream
  `audit_context/2` helper writes the correct audit row regardless of caller shape.

### Test coverage (LOCKED — required for goal-backward verification)
- **D-21.1-04:** Add an integration-style test that:
  - Runs `BulkActions.run(repo, [id1, id2, id3], &Metadata.refresh/2, audit: %{actor: "...",
    cause: "live_admin_bulk_refresh_metadata"})`
  - Asserts 3 `metadata.applied` audit-ledger rows with the same `correlation_id`
  - Asserts each row's `actor` / `cause` equal the BulkActions audit map values
- **D-21.1-05:** Add a unit/integration test for single-connection refresh that asserts
  top-level `actor:` / `cause:` opts (no `audit:` wrapper) still produce a valid audit
  ledger row (regression guard for `LiveAdmin` single-action and `AutoRefresh` paths).
- **D-21.1-06:** Existing Phase 20 / Phase 21 tests must continue to pass without
  modification (no breaking change to public `Refresh.refresh/2` semantics).

### Telemetry
- **D-21.1-07:** No new `:telemetry` events. The `[:metadata, :refresh]` span at
  `lib/relyra/metadata/refresh.ex:28` already covers bulk and single calls; correlation_id
  is observable downstream via the audit ledger and the existing telemetry attached in
  Phase 21-04.

### Backward compatibility
- **D-21.1-08:** Public spec `@spec refresh(binary(), keyword()) :: {:ok, struct()} |
  {:error, Error.t()}` does NOT change. New behavior is additive (read `opts[:audit]` when
  present) and preserves the existing top-level keyword interpretation.

### Claude's Discretion
- Exact internal helper shape (single `resolve_audit/1` private fn vs. inline `Map.merge`)
  is a planner-level mechanical choice.
- Test file placement (extend existing `test/relyra/metadata/refresh_test.exs` vs. add
  `test/relyra/metadata/refresh_bulk_audit_test.exs`) — planner picks per existing test
  organization conventions.

</decisions>

## Specific Ideas

- The fix is genuinely 5–15 lines in `lib/relyra/metadata/refresh.ex`. The audit doc's
  `fix_hint` is exhaustive: "Have Refresh.refresh/2 forward `audit:` into apply_revision
  opts (or merge correlation_id into revision_attrs). Localized change in
  lib/relyra/metadata/refresh.ex:52-65, no schema impact."
- Pattern reference for the cohesive `audit:` shape: see Phase 21 `D-39` audit-seam
  contract (`audit: %{actor:, cause:, correlation_id:}` end-to-end).
- The bulk path's correlation_id is generated by `BulkActions.run/4` at
  `lib/relyra/ecto/bulk_actions.ex:16` (`Ecto.UUID.generate()` if absent). Refresh just
  needs to forward, not generate.
