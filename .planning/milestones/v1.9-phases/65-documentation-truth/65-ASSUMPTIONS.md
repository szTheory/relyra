# Phase 65: Documentation Truth - Assumptions & Gray Areas

## Assumptions

### 1. Adopter-Facing Testing API Migration
- **Assumption:** Adopter-facing documentation will entirely replace references to `Relyra.TestSupport` and `Relyra.TestSupport.FakeIdP` with the public `Relyra.Testing` and `Relyra.Testing.Phoenix` APIs.
- **Why this way:** Phase 64 shipped `Relyra.Testing` as a public, data-first alternative. Adopters using Hex packages will crash on `UndefinedFunctionError` if they try to use `TestSupport` since it's restricted to private repo compilation (`mix.exs`).
- **Files affected:** `README.md`, `guides/overview.md`, `guides/getting_started.md`, `guides/jtbd_user_flows.md`, `guides/recipes/*.md`, `guides/case_studies/phoenix_saas_tenant_onboarding.md`.

### 2. Macro-to-Data API Rewrite in Code Examples
- **Assumption:** Snippets showing `use Relyra.TestSupport, endpoint: ...` and stateful macros (`setup_saml_connection/2`, `build_saml_response/0`) will be rewritten to use explicit fixture generation (`Relyra.Testing.signed_success/1`) and `Relyra.Testing.Phoenix.post_response/5`.
- **Why this way:** The `guides/getting_started.md` heavily relies on macro injection for Section 3 ("Prove local login"). The new API intentionally avoids `use` and application environment mutations, matching Elixir's idiomatic preference for explicit data (like `Plug.Test.conn/3`).

### 3. Batteries Included Output & Internal Demo
- **Assumption:** `BATTERIES_INCLUDED.md` and its generating task (`lib/mix/tasks/relyra.batteries_included.ex`) will be updated to replace `Relyra.TestSupport.FakeIdP` with `Relyra.Testing` as the "local-first proof" standard.
- **Assumption:** The installer and its output will be swept to reflect the new `Relyra.Testing` API.

## Architecture Decisions (Resolved Gray Areas)

Following deep ecosystem research (Elixir/Phoenix/Plug idiomatic patterns, developer ergonomics, and the overarching project vision of "adopter honesty"), we have established a cohesive, one-shot set of recommendations for Phase 65:

### 1. Test Forking over Renaming
**Decision:** Fork the demo test into a public `test/testing_demo_test.exs` that leverages the new `Relyra.Testing` API. The old `test/test_support_demo_test.exs` will be sequestered as a purely internal CI integration proof (e.g., `test/internal/test_support_integration_test.exs` or explicitly marked internal).
**Rationale:** This additive forking retains macro test coverage for our internal CI engine while strictly isolating the public API and setting correct adopter expectations. The public demo test becomes the authoritative, copy-pasteable source of truth for the Getting Started guide. It enforces a single, explicit testing paradigm for adopters without losing our internal end-to-end proof of the `TestSupport` engine.

### 2. Complete Substitution in BATTERIES_INCLUDED.md
**Decision:** `BATTERIES_INCLUDED.md` will explicitly claim `Relyra.Testing` + `Relyra.Testing.Phoenix` for the "local-first proof" and point to the new `test/testing_demo_test.exs`.
**Rationale:** To satisfy the principle of least surprise, all public surfaces—even those generated by internal tools—must aggressively present `Relyra.Testing` as the single, authoritative source of truth. Mixing internal CI testing narratives into public-facing root documentation creates confusion. 

### 3. Aggressive Installer Sweep
**Decision:** The `mix relyra.install` task output, scaffolding, and associated docs will be aggressively swept to eradicate mentions of `TestSupport` and `FakeIdP`.
**Rationale:** The installer is often the very first DX touchpoint. Referencing an API that doesn't ship in Hex immediately breaks trust. Updating the installer output ensures a cohesive, error-free onboarding journey that aligns perfectly with the explicit, data-first nature of Elixir.
