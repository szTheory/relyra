## Warnings

### WR-01: Metadata is reported as saved without parsing or persisting it

**File:** `/Users/jon/projects/relyra/demo/ledger_loop/lib/ledger_loop_web/live/setup_live.ex:42-44`
**Issue:** Any client-provided `metadata` value, including an empty or malformed XML document, only toggles the in-memory `:metadata_saved` flag. The UI then renders “Metadata saved successfully!” even though no metadata source/revision, connection update, validation, or same-transaction audit row has been written. An operator can believe an IdP trust change is active when the seeded connection is completely unchanged.
**Fix:** Route this event through the existing metadata ingestion/validation seam, persist the resulting metadata revision and audit record atomically, and render success only after that call returns `:ok`. If the demo must remain read-only, remove the editable form and replace it with an explicit seeded-example notice.

### WR-02: An arbitrary `set_step` payload can crash the LiveView

**File:** `/Users/jon/projects/relyra/demo/ledger_loop/lib/ledger_loop_web/live/setup_live.ex:46-49`
**Issue:** `String.to_existing_atom/1` raises `ArgumentError` for a forged `phx-value-step` that does not name an already-loaded atom. LiveView event payloads are client-controlled, so a request such as `set_step` with `step=not_a_step` terminates the view instead of being rejected gracefully. Existing-atom payloads outside `@steps` also put the view in an unrendered state.
**Fix:** Use a fixed string-to-step map and reject values outside it, for example:

```elixir
@steps_by_name Map.new(@steps, &{Atom.to_string(&1), &1})

def handle_event("set_step", %{"step" => name}, socket) do
  case Map.fetch(@steps_by_name, name) do
    {:ok, step} -> {:noreply, assign(socket, :active_step, step)}
    :error -> {:noreply, socket}
  end
end
```

### WR-03: “Enable Connection” is a no-op while the screen presents it as a completed state

**File:** `/Users/jon/projects/relyra/demo/ledger_loop/lib/ledger_loop_web/live/setup_live.html.heex:203-205`
**Issue:** This button has neither `phx-click` nor a form action, so activating it changes no connection state. In the same step, the receipt immediately presents the pre-seeded connection as “Verified (enabled),” independent of whether metadata was actually saved or a test login succeeded. That makes the operator-facing setup flow claim an enablement result it did not perform.
**Fix:** Implement an authenticated enable action that checks the required metadata/test evidence before updating the connection through the audited mutation seam; otherwise remove/disable the control and label the page as a read-only walkthrough.
