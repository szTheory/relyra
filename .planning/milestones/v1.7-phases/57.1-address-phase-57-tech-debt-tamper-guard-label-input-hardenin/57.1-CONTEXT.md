<domain>
## Phase Boundary

Close the correctness, robustness, and hygiene debt surfaced by the Phase 57
code review of the demo FakeIdP browser-login proof. **All code changes are
confined to `demo/ledger_loop`** (the host demo app) — this phase does NOT touch
Relyra core, public API, algorithm/trust policy, or the strict verifier gate.

The demo FakeIdP is a deliberately-labelled, dev/test-only local test IdP. Its
job is to produce a genuine cryptographic pass (success path) and a genuine
typed rejection (`:digest_mismatch`, tamper path). The debt items below all
protect that proof's integrity: a tamper helper that can silently fail to tamper
turns the rejection proof into a false negative; unescaped/unbounded untrusted
input on the unauthenticated FakeIdP endpoints is an avoidable crash/amplification
surface; a UI label that lies about the emitted subject erodes trust in a harness
whose entire value is fidelity.

Out of scope (explicitly): hosted broker, production IdP, public API shape
changes, default-tightening, security-posture relaxation, Keycloak promotion.
</domain>

<decisions>
## Implementation Decisions

All five Phase 57 review **Warnings** are LOCKED in scope, plus repo hygiene and
two safety-relevant **Info** items (IN-02, IN-03). IN-01 (cert caching) and IN-04
(comment-only) are deferred.

### Tamper guard (WR-05) — `demo/ledger_loop/lib/ledger_loop/fake_idp/signer.ex:101-106`
- `tamper/1` currently does `String.replace(xml, ~r/<NameID>([^<]+)<\/NameID>/, "<NameID>TAMPERED</NameID>")`.
- The regex matches only a bare `<NameID>` open tag (no attributes, no namespace prefix). If `response_xml/3` ever adds a `Format` attribute or a prefix, `tamper/1` becomes a silent no-op and returns a *valid* signed Response — the "Invalid Login (Tampered Signature)" path would unexpectedly SUCCEED.
- **Decision:** Make the no-op detectable. Broaden the match to `<NameID[^>]*>([^<]+)</NameID>` and **raise** if the replacement did not change the bytes (`tampered == xml` → raise "tamper/1 failed to locate <NameID>; template drifted"). A tamper helper must never silently fail to tamper.

### Login form label (WR-02) — `login.html.heex:34` vs `fake_idp_controller.ex:31`
- The radio label reads "Valid Login (evaluator@example.com)" but `conn_fields/0` hardcodes `name_id: "sarah@northstar.example.com"`. `evaluator@example.com` is NOT a seeded `SAMLIdentity` subject (only `sarah@...` and `chen@...` are seeded by `Fixtures.saml_identities/0`).
- **Decision:** Make the label match the emitted subject — label the valid-login option `sarah@northstar.example.com` (the single source of truth remains `conn_fields/0`). Do not invent a new seeded subject.

### Input hardening — XML escaping (WR-01) — `signer.ex:138-166` + `fake_idp_controller.ex:116-124`
- `extract_in_response_to/1` pulls the `ID` attribute from the inbound (browser-supplied, deflated base64) `SAMLRequest` and threads it as `in_response_to`. `response_xml/3` interpolates it **raw** into `InResponseTo="#{fields.in_response_to}"`. The `[^"]+` capture excludes `"` (no attribute breakout) but allows `<`, `>`, `&` → malformed emitted XML → unhandled `MatchError` crash when the signer re-parses its own output.
- **Decision:** XML-escape interpolated values in `response_xml/3` (at minimum the externally-influenced `in_response_to`; escaping all interpolated fields is acceptable and preferred for uniformity), AND tighten the extractor regex to the SAML `ID` (xsd:ID / NCName) grammar so non-name characters are rejected before reaching the template (defense in depth — see IN-03).

### Input hardening — unknown `idp_action` (WR-03) — `fake_idp_controller.ex:65-98`
- `action = params["idp_action"] || "success"` only defaults on absence; the `case action do "success" -> ...; "failure" -> ... end` has no catch-all, so any other posted value (`idp_action=foo`, array/map from crafted multipart) raises `CaseClauseError` → 500 on an unauthenticated POST.
- **Decision:** Add a catch-all clause. Treat any non-`"failure"` value as the success path (i.e. `case action do "failure" -> ...tampered... ; _ -> ...success... end`). Fail safe, no 500.

### Input hardening — bounded inflate (WR-04) — `fake_idp_controller.ex:126-139`
- `inflate/1` does a single-shot `:zlib.inflate/2` on browser-supplied bytes with no decompressed-size cap → small crafted `SAMLRequest` can inflate to a very large binary (zip-bomb amplification), then scanned by `Regex.run` over the whole string.
- **Decision:** Bound the decompressed output (e.g. cap accepted compressed-input length up front and/or loop `:zlib` with a byte ceiling), and **fail closed to `nil` on overflow** — consistent with the existing "garbled input → nil" contract (`extract_in_response_to` already returns `nil` on any error). Pick a generous-but-finite ceiling appropriate for a SAML AuthnRequest.

### Info — descriptive PEM-decode error (IN-02) — `keypair.ex:58`
- `[entry] = :public_key.pem_decode(pem_bin)` hard-matches a single-entry PEM; a multi-entry file raises a bare `MatchError` with no context.
- **Decision:** Pattern-match the expected entry type and raise a descriptive error on mismatch. Diagnosability only — no behaviour change for the correct demo key.

### Info — anchor ID regex (IN-03) — `fake_idp_controller.ex:119`
- `~r/\bID="([^"]+)"/` returns the *first* `ID` attribute anywhere in the document, not specifically the root `AuthnRequest/@ID`.
- **Decision:** Tightening for WR-01 already constrains the captured grammar; additionally anchor to the root element's `ID` OR document the first-match assumption with a comment. Reusing the `SaxyTree` engine already imported in `Signer` to read the root `attrs` is acceptable but optional — a tightened+anchored regex with a clarifying comment is sufficient for a demo harness.

<specifics>
## Specific Ideas

- The success path and tamper path are both exercised by the demo's test suite (`mix ci.demo_app`) and by the existing Phase 57 plans/summaries. Any fix to `tamper/1` or `idp_action` handling must keep the existing success + `:digest_mismatch` rejection behaviour intact.
- `tamper/1` raise-on-no-op is itself the highest-value fix: it is a regression guard for the rejection proof. Prefer a dedicated test asserting that tampering a current `response_xml/3` output still changes the bytes (proves the guard does not fire today) AND that the helper raises when handed XML with no matching `<NameID>`.
- `extract_in_response_to` already encodes a "garbled input → nil" contract (controller lines 113-124). WR-04's overflow handling must extend that same fail-closed contract, not introduce a new error mode.
</specifics>
