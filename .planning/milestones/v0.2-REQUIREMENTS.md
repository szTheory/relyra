**Core Value:** Every SAML login ends in a verified trust path or a typed rejection — never a silent compromise.

## v0.2 Requirements

Committed scope for v0.2: enterprise configuration. All five requirements verified, manual sign-off recorded, and re-audited 2026-05-06 with status `passed` (5/5).

### Enterprise Configuration

- [x] **CFG-01**: User can create and maintain tenant-scoped SAML connection records backed by Ecto schemas and migrations.
  - **Outcome:** validated. `Relyra.Ecto.Connection` aggregate with internal binary PK + public `connection_id` join key, lifecycle status, child certificate inventory. Migrations create connection and certificate tables with FK behavior. `Relyra.Ecto.Connections` exposes a minimal create/update/enable/disable API; runtime-readiness is a separate explicit gate. Phase 07 verified 5/5 (2026-05-05).

- [x] **CFG-02**: Relyra can resolve a persisted connection into a runtime snapshot for login and metadata flows.
  - **Outcome:** validated. `Relyra.ConnectionResolver.Ecto` returns a normalized `%Relyra.Connection{}` runtime snapshot via `Relyra.Ecto.ConnectionLoader` + `Relyra.Ecto.ConnectionSnapshot`. No Ecto rows leak above the resolver boundary. Login, metadata, and protocol validation all consume the same canonical snapshot with `idp_certificates` precedence. Phase 08 verified 5/5 (2026-05-05).

- [x] **CFG-03**: User can import and export metadata for a connection and trigger a controlled refresh with provenance.
  - **Outcome:** validated. `Relyra.Metadata.import_xml/3`, `register_source/3`, and `refresh/2` provide explicit metadata onboarding and operator-triggered refresh. `Relyra.Ecto.MetadataApply` is a single transactional write seam; failed attempts persist as revision rows without mutating runtime trust; last-known-good preserved on failure; new signing certs stage as `:next` (no implicit trust shift). HTTPS endpoint precedence: HTTP-Redirect → HTTP-POST → remaining. Telemetry redacted. Verified via Phase 12 (`09-VERIFICATION.md`, 2026-05-06; serial smoke 15/15; full suite 168/168).
  - **Note:** Repaired in Phase 12 — initial Phase 09 implementation had a `:invalid_certificate_pem` regression flagged by the 2026-05-05 audit. Phase 12 normalized metadata certificate handling in `Import.build_candidate/1`.

- [x] **CFG-04**: User can manage certificate inventory for a connection with expiry tracking and staged rollover.
  - **Outcome:** validated. `Relyra.Ecto.CertificateInventory` owns the `:active` / `:next` / `:retired` lifecycle with per-cert `not_before` / `not_after` facts. Promotion, retirement, and rollback are explicit, optimistic-locked, and produce typed `:conflict` errors on stale writes. Snapshot hydrates only `:active` certs into runtime trust. Verified via Phase 13 (`10-VERIFICATION.md`, 2026-05-06; serial rollover packet 23/23; manual sign-off recorded).

- [x] **CFG-05**: User can persist attribute/group mapping configuration and review a durable audit history of trust changes.
  - **Outcome:** validated. `Relyra.Ecto.AttributeMapping`, `Relyra.Ecto.GroupMapping`, and `Relyra.Ecto.MappingRevision` (append-only ledger) persist mappings per connection. `Relyra.Ecto.MappingCommands` co-commits live row replacement + revision ledger row + audit event row in one transaction. Runtime consumers see plain `mapping_config` maps via `Relyra.Ecto.ConnectionSnapshot`; `Relyra.UserMapper.DefaultAttribute` consumes persisted rules first with legacy fallback. Cross-domain audit hardening (Plan 11-03) extends same-transaction audit capture to connection, metadata, and certificate writes. Verified via Phase 14 (`11-VERIFICATION.md`, 2026-05-06; serial mapping/audit packet 62/62; manual sign-off recorded).

## Deferred to v1 (carried forward)

- **CFG-06**: User can manage enterprise configuration through an optional LiveView admin surface. Reserved for v0.3 adoption-UX milestone now that config storage is stable.
- **CFG-07**: User can run bulk operations across multiple connections. Useful later; not needed to prove the trust-data model.
- **CFG-08**: User can enable scheduled metadata refresh automation with guardrails. v0.2 shipped explicit operator-triggered refresh; automation waits until provenance is proven in adopter use.

## Out of Scope (Confirmed)

| Feature | Reason | Outcome |
|---------|--------|---------|
| Hosted SSO broker / SaaS runtime | Relyra is a library; customer data and control stay in host applications. | Confirmed; no drift. |
| OIDC/OAuth in-core | Relyra is SAML-specific; OIDC/OAuth belongs to adjacent libraries. | Confirmed; no drift. |
| Generic auth framework (passwords/MFA/session system) | Session establishment is delegated via `SessionAdapter`; host app owns auth domain. | Confirmed; no drift. |
| Production IdP implementation | `Relyra.TestSupport.FakeIdP` is dev/CI support only, not a product IdP. | Confirmed; no drift. |
| SCIM lifecycle ownership | Relyra focuses on login-time identity assertion and mapping, not full lifecycle provisioning. | Confirmed; no drift. |
| Security-by-marketing claims (bulletproof/unhackable/military-grade) | Brand and security discipline require precise, falsifiable claims only. | Confirmed; no drift. |
